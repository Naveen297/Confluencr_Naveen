# Transaction Ledger

A ledger API for accounts with credit and debit transactions, plus a React web app on top of it.

- **Backend:** Python, FastAPI, SQLite
- **Frontend:** React 18, Vite
- **Tests:** pytest (58 tests)

The API and the web app run together on one port with a single command.

---

## Getting started

### Prerequisites

- **Python 3.9 or newer.** Check with `python3 --version`.
- Node.js 18+ is **optional**. A production build of the frontend is already in `frontend/dist`. You only need Node if you change the React code.

> If your Python is older than 3.9 (for example a conda `base` environment on 3.8), create a fresh environment first:
>
> ```bash
> conda create -n ledger python=3.11 -y
> conda activate ledger
> ```

### Quick start

```bash
python3 run.py --seed
```

This creates a virtual environment in `.venv`, installs the dependencies, starts the server and opens http://localhost:8000. `--seed` adds a few demo accounts; leave it off to start with an empty database.

### Manual setup

```bash
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
python run.py --seed
```

Stop the server with `Ctrl + C`. Next time, activate the environment and run `python run.py`.

### Useful commands

| Command | Description |
| --- | --- |
| `python run.py` | Start the app at http://localhost:8000 |
| `python run.py --seed` | Add demo accounts if the database is empty |
| `python run.py --test` | Run the backend test suite |
| `python run.py --dev` | Hot reload: API on :8000, Vite dev server on :5173 (needs Node) |
| `python run.py --reset` | Delete the local database |
| `python run.py --port 9000 --no-browser` | Use another port; don't open a browser tab |

The interactive API docs (Swagger UI) are at **http://localhost:8000/api/docs**.

### Rebuilding the frontend

`run.py` rebuilds automatically when Node is installed and the sources have changed. To build by hand:

```bash
cd frontend
npm install
npm run build
```

## Requirements checklist

| Requirement from the brief | Where / how |
| --- | --- |
| **Create account** with `id`, `name`, `balance`, `created_at` | `POST /api/accounts` |
| `id` is unique | UUID4, `PRIMARY KEY` in the database |
| `name` is required | Validated (1–100 chars, whitespace trimmed); blank names return `422` |
| Initial balance is always 0, and the client can't set it | Hard-coded `0` on insert; a request containing `balance` is rejected with `422` |
| `created_at` is generated by the system | UTC ISO-8601 timestamp set by the server |
| **Add transaction** with `id`, `account_id`, `type`, `amount`, `description`, `reference_id`, `created_at` | `POST /api/accounts/{id}/transactions` |
| Credit increases the balance | `balance + amount`, in the same database transaction as the insert |
| Debit decreases the balance | `balance - amount` |
| Debit rejected when the balance is too low | `422 INSUFFICIENT_FUNDS`; nothing is written |
| `reference_id` unique per account | `UNIQUE (account_id, reference_id)` plus an application check |
| Duplicate: no new transaction, no balance change, clear response | `409 DUPLICATE_TRANSACTION`, with the original transaction in `details` |
| Same `reference_id` allowed on different accounts | Uniqueness is scoped to the account |
| **Get balance** with `account_id` and `balance` | `GET /api/accounts/{id}/balance` |
| Missing account returns an error | `404 ACCOUNT_NOT_FOUND` |
| **Transaction history**: filter by `credit` / `debit`, or both | `GET /api/accounts/{id}/transactions?type=` |
| Pagination with `page` and `limit` | Response includes `page`, `limit`, `total_records`, `total_pages`, `has_next`, `has_previous` |
| Latest first by `created_at` | `ORDER BY created_at DESC, seq DESC` (insertion order breaks ties) |
| **Immutability**: transactions can't be edited or deleted | No PUT, PATCH or DELETE routes (`405`); database triggers also block `UPDATE` and `DELETE` |
| **Balance consistency** | All checks and writes run in one `BEGIN IMMEDIATE` transaction; tests confirm balance = Σcredits − Σdebits |
| Failed or rejected transactions don't affect the balance | The whole transaction rolls back; covered by tests |

## API reference

Base path: `/api`. Request and response bodies are JSON. Amounts are numbers with at most two decimal places.

### `POST /accounts`

```json
{ "name": "Asha Raman" }
```

`201 Created`

```json
{
  "id": "6f1c2a9e-7b1d-4b7a-9a52-1c1b0f3d2e11",
  "name": "Asha Raman",
  "balance": 0,
  "created_at": "2026-10-27T12:51:03.114902Z"
}
```

### `POST /accounts/{account_id}/transactions`

```json
{
  "type": "debit",
  "amount": 30,
  "description": "Electricity bill",
  "reference_id": "BILL-2610"
}
```

| Result | Status | `error.code` |
| --- | --- | --- |
| Created | `201` | |
| Account not found | `404` | `ACCOUNT_NOT_FOUND` |
| Debit exceeds the balance | `422` | `INSUFFICIENT_FUNDS` |
| `reference_id` already used on this account | `409` | `DUPLICATE_TRANSACTION` |
| Invalid input | `422` | `VALIDATION_ERROR` |

A created transaction also includes `balance_after`, the account balance right after that entry.

### `GET /accounts/{account_id}/balance`

```json
{ "account_id": "6f1c2a9e-…", "balance": 100.0, "as_of": "2026-10-27T12:55:40.020117Z" }
```

### `GET /accounts/{account_id}/transactions`

| Query param | Default | Notes |
| --- | --- | --- |
| `type` | (none) | `credit` or `debit`; omit for both |
| `page` | `1` | 1-based |
| `limit` | `10` | 1–100 |

```json
{
  "account_id": "6f1c2a9e-…",
  "type": "credit",
  "data": [
    {
      "id": "…",
      "account_id": "6f1c2a9e-…",
      "type": "credit",
      "amount": 50.0,
      "description": "Refund",
      "reference_id": "RF-1",
      "balance_after": 150.0,
      "created_at": "2026-10-27T12:58:10.402113Z"
    }
  ],
  "pagination": {
    "page": 1,
    "limit": 10,
    "total_records": 23,
    "total_pages": 3,
    "has_next": true,
    "has_previous": false
  }
}
```

### Other endpoints

| Method | Path | Description |
| --- | --- | --- |
| `GET` | `/accounts` | All accounts, newest first. `?search=` matches name or id prefix |
| `GET` | `/accounts/{id}` | Account with totals (credits, debits, counts) |
| `GET` | `/accounts/{id}/transactions/{transaction_id}` | A single transaction |
| `GET` | `/health` | Health check |

### Error format

All errors share one shape:

```json
{
  "error": {
    "code": "INSUFFICIENT_FUNDS",
    "message": "Insufficient balance. The debit was rejected and the balance is unchanged.",
    "details": { "balance": 100.0, "requested": 150.0, "shortfall": 50.0 }
  }
}
```

### Example with curl

```bash
# create an account
curl -s -X POST localhost:8000/api/accounts \
  -H 'Content-Type: application/json' -d '{"name": "Asha"}'

# credit 100 (replace ACCOUNT_ID with the id from the response above)
curl -s -X POST localhost:8000/api/accounts/ACCOUNT_ID/transactions \
  -H 'Content-Type: application/json' \
  -d '{"type": "credit", "amount": 100, "description": "Opening deposit", "reference_id": "DEP-1"}'

# balance
curl -s localhost:8000/api/accounts/ACCOUNT_ID/balance

# debits only, page 1
curl -s "localhost:8000/api/accounts/ACCOUNT_ID/transactions?type=debit&page=1&limit=10"
```

## Design notes

**Money as integers.** Amounts are validated as `Decimal` with at most two decimal places and stored as integer minor units (paise or cents). Repeated small amounts never cause rounding drift. For example, ten credits of `0.10` minus a debit of `0.30` gives exactly `0.70`.

**One atomic step per transaction.** Posting opens `BEGIN IMMEDIATE`, which takes SQLite's write lock before the first read. It then checks for a duplicate, checks funds, updates the balance and inserts the row. Any failure rolls the whole thing back. Because the lock is held from the read to the write, concurrent requests can't spend the same money twice. A test fires 25 parallel debits at an account that can only cover 10, and exactly 10 succeed.

**Guard rails in the schema.** The database enforces the rules too, not only the application code:
- `CHECK (balance >= 0)` on accounts
- `UNIQUE (account_id, reference_id)` on transactions
- triggers that abort any `UPDATE` or `DELETE` on transactions

**Duplicates.** A repeated `reference_id` returns `409` together with the original transaction, so a client retrying after a timeout can see what was actually recorded. A rejected debit is never stored, so its reference can be used again later.

**Running balance.** Each transaction stores `balance_after`. The history works as a statement, and you can check any entry without replaying the account.

## Web app

- Accounts sidebar with search, and a dialog to open a new account
- Account header: balance, total credits and debits, entry count, copyable account id
- Entry form with a Credit/Debit switch and an auto-generated (editable) reference id. It warns before a debit larger than the balance, and shows duplicate and insufficient-funds responses inline.
- Transaction history as a ledger: Debit, Credit and running Balance columns, All/Credits/Debits filter, page numbers and page size
- Click a row for full details. Entries are read-only.
- Light and dark themes (follows the system setting the first time, then remembers your choice)
- Responsive down to phone width
- The selected account is kept in the URL (`?account=…`), so refresh and back/forward work as expected

## Assumptions

- A duplicate `reference_id` is rejected even if the amount or type differs; the first transaction wins.
- Rejected transactions are not stored.
- No authentication or currency handling. Amounts are shown without a currency symbol.
- SQLite keeps the project self-contained. On Postgres the same approach maps to `SELECT … FOR UPDATE` on the account row.
